Canonical UI definition visibility uses the configured Forge catalog and its shared resource resolver. Current authenticated users see metadata by default; explicit role or feature requirements can hide definitions. Datasources and actions retain separate current authorization. Legacy workspace-ID/window-key authorization callbacks apply only to legacy catalogs.

`ui/view:get` and `ui/view:open` accept an optional `resource` reference (`uri`, optional `revision`). URI-only requests are supported. A configured catalog ID owns its resource even when its reusable browser activation key is `reportBuilder`; a denied catalog ID never falls through to that renderer's resource. Get/open authorize the exact requested candidate without first requiring list's omitted selection.

Open carries the full selected server pin through the Forge bridge's `resolvedResource` input. The bridge verifies fingerprint, principal/account/authority binding and lease before serving approved inline metadata. Instance IDs distinguish content/revision/authority identities. Open results and protected window/datasource responses include the same resource pin.

Live registry snapshots pass through Forge's server-held instance filter before ingestion. Browser resource text and metadata cannot replace the approved resource definition. Undeclared datasource refs are removed. A minimal system chat anchor and routing envelope permit the first protected open; business instances require server pins.

Archived lifecycle events require current revalidation of the original server-held resource pin, including its actual namespace/client/instance identity. Context-aware event APIs are `ListEventsContext`, `ListConversationEventsContext`, `FindAuthorizedConversationWindowContext`, `RecordEventContext`, and `RecordConversationEventContext`. No-context legacy event APIs reveal no events in canonical mode. Reused instance IDs, expired pins, changed content, changed account/identity and revoked permissions cannot resurrect an archived event.

Window/datasource commands carry a revalidated pin through `requestctx.WithResolvedResource`. A wire pin may constrain a request; it supplies no authority. The Forge bridge still requires the host's `ResolvedWindowAuthorizer` for action and selected-input checks before and after dispatch. Browser HTTP datasource execution must independently recover/revalidate the server instance pin and compare actual backend dependency fingerprints.
